## 1. 六类要素的判定标准

要素"写到"的判定标准不是"出现了这个词"，而是"读者能否据此执行/复核"：

| 要素 | 合格判据 | 不合格（视为缺失） |
|------|----------|--------------------|
| 步骤 | 有序编号，每步含输入/操作/输出/判断条件 | 一段流水账，无法拆出单步 |
| 实验设置 | 硬件型号、软件版本、种子、重复次数俱全或有[待确认]标注 | 只写"在 GPU 上训练" |
| 参数 | 每个参数有取值、单位、作用对象、来源 | 只有零散数值埋在句子里 |
| 数据集 | 名称+版本+规模+预处理+划分比例+随机方式 | 只有数据集名字 |
| 对照 | 基线有版本、条件同预算、指标有统计方式 | "优于现有方法"一句话 |
| 复现与限制 | 代码/环境/命令/数据获取五项清单；限制落到失效场景 | "代码将开源"一句空话 |

六类要素在成稿中必须有**可定位的章节或小节标题**，不得只散落在段落里——selfcheck.py 按关键词组核查。

## 2. 参数一致性规则（写得准）

1. **单一事实源**：每个参数只有一个"规范取值"，写在参数表里；正文引用规范值，不在多处各写一份。若体裁要求正文必须出现数值，则该数值必须与参数表逐字符一致（含单位写法）。
2. **单位归一**：同一参数全文用一种单位。温度统一 K 或 ℃；学习率统一科学计数或小数，不混用；显存统一 GB 或 GiB 并注明。
3. **精度保持**：材料里是 `lr=0.0003` 就写 0.0003，不四舍五入成 3e-4 除非确认数值精确相等；1e-3 与 0.001 数值相等可互换但全文统一写法。
4. **默认值标注**：沿用框架默认值的参数，若材料可证明（如代码未设置该参数），写"采用 PyTorch 默认初始化 [S2]"；不可证明则不写。
5. **作用对象写清**：学习率是哪个优化器的、dropout 加在哪一层、权重衰减作用于哪些参数组——材料有则写，没有标 [待确认]。
6. **param_check.py 是底线不是上限**：脚本只能发现"键=值"形态的冲突；语义层面的冲突（如"训练 100 轮"与"early stop 在第 37 轮触发"并存且未解释）必须人工通读排查。
7. **观察值 vs 配置值（v2 取舍规则）**：命令行与日志中实际加载/打印的**观察值**是本次实验真实使用值，进正文；配置文件中被覆盖的**旧值**进参数表"被覆盖值"列与冲突记录——论文与日志两侧同时保留，任何一侧都不得丢弃。**拦截规则**：想把被覆盖的旧值写成"本次采用"时，必须先找到该值被实际加载的证据（日志加载行、命令行 flag、运行记录）；找不到就禁止写"本次采用"，只能写"配置记录值（未证实加载）"并标 [待确认]。param_check.py 的冲突 FAIL 是此拦截的机器兜底；只抽取 config/code 而不以实际运行为依据的行文（光抽取无出处分级与冲突处置）视为不合格。
8. **阶段级出处（stage-specific provenance）**：每个参数标注它属于哪个阶段/哪次运行（预处理/训练/评测；run 1/2/3）。同名参数跨阶段取值不同不算冲突——参数表分行登记并注明阶段；正文引用时写清"训练阶段 lr=0.01 [S3: run3]"这种粒度。跨阶段共用一个值时注明"三阶段共用"。
9. **曲线与指标数值**：引用日志中的曲线/指标时，只写材料明确给出的首尾值（初始值/最终值）或有行号可指的极值点，不目测、不内插中间点；数值挂来源到具体运行与行号（如"训练损失由 2.31 降至 0.18 [S3: run3 L88/L204]"）。
10. **证据编号**：参数表各行与正文关键论断在 evidence_map.md 中有对应证据编号（E# → S# + 位置）；交付前按编号抽查"已支持行"确实可回溯。

## 3. 来源标注规则

1. 每个含**数值、版本号、数据集事实、性能结论**的句群，末尾挂 `[S#]`；S# 来自 materials_register.md 的编号。
2. 标注到具体位置：`[S2: config.yaml L12]`、`[S3: train.log 第 4 次运行]`，在 evidence_map.md 中展开。
3. 一句多源时全部列出：`batch size 32、学习率 1e-3 [S2, S4]`。
4. 作者口头/笔记提供的参数，来源标笔记材料并加注"（作者笔记，未经日志核验）"。
5. **禁止**：为让段落通顺补出材料中没有的数值、版本、引用——这是本题红线，发现一处即回第 3 步清除并记 change_log。

## 4. 冲突与缺口的处置规则

1. **配置 vs 日志冲突**：优先查日志中实际加载/打印的参数；日志也查不到时，两值并列记入 evidence_map.md，正文写"材料记录不一致（X vs Y），待作者确认"，不擅自二选一。
2. **多版本配置**：以时间戳、日志加载记录、笔记中的实验编号交叉定位最终实验所用版本；定位不了 → 待确认项。
3. **缺口**：材料完全没写的要素，成稿对应小节写"材料未提供 ××，待补充："并列出需要作者提供的具体清单（精确到"训练日志中第几次运行的随机种子"这种颗粒度）。
4. **不确定**：能缩窄范围但不能定值的，写明范围与依据（"显存占用介于 11–16 GB，三次运行峰值不同 [S3]"）。

## 5. 数据集与划分规则

1. 数据集必须带**版本或获取日期/地址**：版本含混是复现失败首因。材料只有名字没版本 → [待确认]。
2. 划分必须写**比例 + 随机方式 + 种子**：如"8:1:1 随机划分，seed=42 [S2]"；"按时间顺序划分，2023 年前为训练集"。
3. 预处理按顺序写步骤（去重 → 缺失值处理 → 归一化 → 增广），每步挂来源。
4. 各子集用途明确：调参只能用验证集，最终报告只用测试集——材料若显示混用，如实写并在限制中指出。

## 6. 可复现性清单（做得着）

交付前逐条自问，读者只读本章节能否重做：

- [ ] 代码：仓库地址/版本号/commit 或"材料未提供"；
- [ ] 环境：OS、Python/框架/关键库版本、CUDA 版本，或指向环境文件 [S#]；
- [ ] 命令：完整可复制的运行命令（含关键 flag），材料有的话；
- [ ] 数据：获取方式与版本；
- [ ] 随机性：种子、重复次数、结果报告方式（均值±标准差？最优值？）；
- [ ] 资源：硬件与单次运行时长量级。

缺项标 [待确认] 并列入 gaps.md，不得略去。

## 7. "写了等于没写"反模式集

以下写法一律视为不合格，必须改写或标注：

1. "我们按照标准流程进行实验。"——无步骤、无条件、无来源；
2. "参数设置如表所示。"——但全文没有这张表，或表里没有来源列；
3. "学习率设置为合适的值。"/ "经过多次调试确定最优参数。"——无取值、无搜索范围；
4. "实验在 GPU 服务器上完成。"——无型号、无数量、无软件版本；
5. "数据集按照常用比例划分。"——无比例、无随机方式、无种子；
6. "与基线相比，我们的方法取得了更好的结果。"——基线无名无版本、指标无统计方式、数值无来源；
7. "本方法存在一定局限性。"——无具体失效场景；
8. "实验结果具有很好的可复现性。"——无种子、无环境、无命令的自夸；
9. 多步操作压一句："数据经过清洗、归一化、增广后输入模型训练至收敛。"——四步操作零细节；
10. 条件串台："模型训练 100 轮，测试集准确率达到 92%。"——把评测结论写进训练设置句，且未说明评测用的是哪个子集。

## 8. 统计与对照的写法规则

1. 性能结论必须带：重复次数、均值与离散度（标准差/置信区间）、显著性检验（方法+阈值），材料有的话；材料只跑了一次就如实写"单次运行结果"。
2. 基线比较必须同预算同数据：不同则写明差异（"基线结果为原文报告值，其训练数据规模大于本文"）。
3. 指标首次出现给定义或出处，全文符号一致。
4. 显著提升必须对应检验结果；"略优于""基本持平"等措辞必须有数值支撑且数值挂来源。
